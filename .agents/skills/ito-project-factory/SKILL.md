# ITO Project Factory

## ワークフロー

1. **一言を案件へ展開**：目標、利用者、現状の課題、目標指標を具体化する。要件が薄い場合は常識的な初期案を採用し「仮定」と記載する。情報不足のために何度も質問しない。
2. **過去成果物を検索**：アクセスできる関連リポジトリ・README・コード・画面・決定履歴を検査する。 `references/REUSE_CATALOG.md` の既存資産を候補に使う。未確認のコードを利用可能と断定しない。私的資料を公開場所へ複製しない。
3. **型を選ぶ**：`references/PROJECT_TYPES.md` から主となる型を選び、必要なものだけ他型から追加する。巨大なフル機能をいきなり作らない。
4. **UIファースト**：`references/UI_RULES.md` に従い画面構成・ナビゲーション・PC/スマホの見え方を定義。参考画像や既定のデザインを優先し、機能やDBより先にモック承認ゲートを置く。
5. **運用まで設計**：`references/ENGINEERING_RULES.md` に従い、データ・役割・外部サービス・監査ログ・承認・バックアップ・監視を選定する。医療・福祉・会計・給与について安全性や正式確認を省略しない。
6. **設計7点を埋める**：`templates/OUTPUT_CONTRACT.md` を読み、 `projects/<英数字slug>/` に PROJECT_BRIEF.md / UI_SPEC.md / ARCHITECTURE.md / DATA_MODEL.md / TASKS.md / PROJECT_STATE.md / CODEX_HANDOFF.md を作る。空の見出しだけで完了にしない。
7. **品質確認**：既存仕様と矛盾がないか、モバイル/PCの画面仕様があるか、MVPが小さいか、セキュリティ境界があるか、P0タスクに完了条件・検証条件があるかを確認。
8. **最小限の報告**：成果物パス、主要な設計選択、要確認事項、次の1タスクのみを回答する。

## 明確な境界

- 「大枠を作る」：文書とUI設計まで。**ソースコードや本番環境は勝手に変更しない**。
- 「UIモックを作る」：テスト用の架空データを使った画面プロトタイプまで。外部サービスと接続しない。
- 「実装して」：既存仕様とUI確定を確認後、コード実装・テスト。公開や不可逆操作は別の承認ゲート。
- 実装できない連携は「未確認」「未実装」とする。検証していないのに「稼働中」と書かない。
- 未公開の実データや認証情報は公開リポジトリへ絶対に書かない。

## 利用者が決めること

ユーザーは見た目、業務上の例外、費用、公開、権限の最終判断をする。技術選定やタスク分解はAIが先回りして提案する。決定・仮定・保留を PROJECT_STATE.md で分ける。
